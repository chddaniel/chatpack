## Deliberately not in scope yet

- **Group features beyond membership, roles, invites, and visibility** - groups
  ship with `admin`/`member`, a name, a 256-participant cap, admin-gated
  management ([ADR 0017](/docs/concepts/architecture)), shareable invite links
  with an optional approval queue ([ADR 0019](/docs/concepts/architecture)), and
  a public/private flag that puts a group in a browsable directory
  ([ADR 0020](/docs/concepts/architecture)). Per-group permission grants,
  mentions, and channel-wide roles beyond `admin`/`member` are not part of it.
  A public channel is discoverable, not readable: browsing the directory grants
  no read access, so reading still means joining.
- **Message threads** - `replyToMessageId` is a flat pointer at one earlier
  message, not a thread tree: no thread ids, no per-thread reply counts, no
  nested pagination. See
  [Conversations & messages](/docs/concepts/conversations-messages).
- **Message formatting** - `body` remains opaque text. Applications choose
  plain text, Markdown, or another syntax and own safe parsing and rendering;
  Chatpack does not parse Markdown or return rendered HTML. See
  [ADR 0022](/docs/concepts/architecture).
- **Push notification providers** - applications can start their own delivery
  work from `afterMessageMutation`, but Chatpack does not ship providers.
- **Reusable React UI package** - Chatpack remains headless. `chatpack init`
  generates editable application-owned UI source, not an `@chatpack/ui` package.
- **Non-participant search access** - the initial search implementation scopes
  storage results to participant conversations; dynamic `canRead` access for
  support/admin users needs a separate design.
- **Moderation beyond the core suite** - Chatpack provides optional blocks,
  mutes, reports, and bans. User identity, notifications, host-session
  revocation, and moderation UI remain application-owned.
- **Multi-node `presence()`** - durable events and typing/receipts relay across
  nodes via [`@chatpack/transport-redis`](/docs/realtime/multi-node), but
  presence counts live SSE connections in an in-process `Map`. Shared
  connection state is a presence change, not a transport one.

Full scope and reasoning in
[docs/MVP.md](https://github.com/chddaniel/chatpack/blob/main/docs/MVP.md).

## Stability

Everything is `0.x` until the public API stabilizes - expect minor breaking
changes before `1.0`. Releases are managed with Changesets; each package has a
`CHANGELOG.md`.

## The longer arc

The vision (see
[docs/ARCHITECTURE.md](https://github.com/chddaniel/chatpack/blob/main/docs/ARCHITECTURE.md))
is BetterAuth-shaped: the obvious open-source default for chat infrastructure -
small core, adapter-driven, extensible via plugins, friendly to both human
developers and AI builders.
