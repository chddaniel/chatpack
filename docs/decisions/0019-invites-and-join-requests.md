# ADR 0019: Invite links and join requests

- **Status:** accepted
- **Date:** 2026-08-08
- **Milestone:** v1.next (groups, part 2)

## Context

ADR 0017 shipped groups with exactly one way in: an admin calls
`addParticipants` with your user id. That closes the loop for apps whose users
already know each other's ids, and it is useless for the two flows every group
product actually needs:

1. **An invite link.** An admin mints a shareable URL; whoever opens it joins.
   The admin does not need to know the invitee's user id - or that they have an
   account yet. This is the only way to invite someone you can't already name.
2. **A join request.** A user asks to join a group they know about; an admin
   approves or denies. The inverse direction, and the moderation half of any
   public or semi-public channel.

ADR 0017 §"Consequences" listed both as deliberately deferred, and
`docs/STATUS.md` recorded why: they "need a pending-membership entity, not a
column." That is the whole difficulty. Every other group operation writes a row
that either exists or doesn't - a participant, a role. An invite is a **secret
that has not been used yet**, and a join request is a **membership that has
been asked for but not granted**. Neither fits the participants table, and both
carry state (uses, expiry, approval status) that no existing table has a column
for.

Questions this ADR settles:

1. One pending-membership entity, or two?
2. Do these methods join the required adapter contract, which grew fourteen →
   nineteen one release ago?
3. Who generates the invite token, and is it stored in plaintext?
4. Does redeeming a link join you, or ask to join?
5. What may a link holder see _before_ they join?
6. Do invites and join requests publish live events?

## Decision

### 1. Two entities, not one `PendingMembership`

`ConversationInvite` and `JoinRequest` are separate types with separate
storage:

```ts
interface ConversationInvite {
  /** The secret. URL-safe, generated by core (see §3). Also the identity. */
  code: string;
  conversationId: string;
  createdBy: string;
  createdAt: Date;
  /** `null` never expires. */
  expiresAt: Date | null;
  /** `null` is unlimited. */
  maxUses: number | null;
  uses: number;
  /** Redeeming creates a join request instead of joining outright (§4). */
  requiresApproval: boolean;
  metadata: Metadata;
}

interface JoinRequest {
  id: string;
  conversationId: string;
  userId: string;
  status: "pending" | "approved" | "denied";
  /** Optional note from the requester, trimmed, ≤ 500 chars. */
  message: string | null;
  /** Set when this request came from redeeming an approval-gated invite. */
  inviteCode: string | null;
  createdAt: Date;
  resolvedAt: Date | null;
  resolvedBy: string | null;
  metadata: Metadata;
}
```

A unified entity with a `direction` discriminator was the obvious first
instinct and it is wrong: the two shapes barely overlap. An invite has a
secret, a use counter and an expiry, and no requester. A join request has a
requester and a resolution, and no secret, no counter, no expiry. Unifying them
means every row has half its columns null - and worse, the two have **opposite
permission models**: creating an invite requires authority over the group,
creating a join request requires _not_ being in it. One table would have to
encode "who may create this row" as a runtime branch on `direction`, which is
two entities wearing one hat.

### 2. Invites are an **optional** adapter capability, exposed as a namespace

`StorageAdapter` gains one optional property, not nine optional methods:

```ts
interface StorageAdapter {
  /** Invite + join-request storage (`docs/decisions/0019`). Optional. */
  invites?: InviteStorage;
}
```

Core checks `storage.invites` once per route and throws a new
`INVITES_UNSUPPORTED` (501) when it is absent - exactly the shape ADR 0015 gave
`searchMessages`.

**Why optional, when ADR 0017 §6 argued groups had to be required.** That
argument was about _semantics_: a membership row is identical on every backend,
unlike search matching, so making groups optional would have fragmented the
interchangeable-adapter promise for a one-time cost. Invites do not fail that
test - a token row is just as backend-neutral as a participant row. They fail a
different one: **the required contract grew fourteen → nineteen methods one
release ago**, and taking it to twenty-eight in the next release, for a feature
a 1:1-only app will never call, converts "write an adapter" from an afternoon
into a project. Unlike groups (which reuse the participants table every DM
already writes) invites need genuinely new tables that a non-group app has no
other reason to create.

So the required contract stays at **nineteen**. The distinction worth keeping:
ADR 0015 made search optional because its _results_ vary per backend; this ADR
makes invites optional because the _feature_ is. Both report a 501 rather than
degrading silently, which is the part that matters.

**Why a namespace rather than nine optional methods.** Nine independently
optional methods have 2⁹ possible states, almost all of them broken - core
would need a check per call site, and an adapter that implemented six of nine
would typecheck and then fail at runtime on the seventh. One optional object is
all-or-nothing: either the capability is there or it isn't. This is a new
pattern for the contract and a deliberate precedent for any future optional
feature bundle.

```ts
interface InviteStorage {
  createInvite(input: CreateInviteInput): Promise<ConversationInvite>;
  getInvite(code: string): Promise<ConversationInvite | null>;
  listInvites(conversationId: string): Promise<ConversationInvite[]>;
  deleteInvite(input: DeleteInviteInput): Promise<void>;
  /** Atomically consume one use; `null` if no longer usable (see below). */
  consumeInvite(code: string): Promise<ConversationInvite | null>;
  createJoinRequest(input: CreateJoinRequestInput): Promise<JoinRequest>;
  getJoinRequest(input: GetJoinRequestInput): Promise<JoinRequest | null>;
  listJoinRequests(input: ListJoinRequestsInput): Promise<JoinRequest[]>;
  resolveJoinRequest(input: ResolveJoinRequestInput): Promise<JoinRequest>;
}
```

**`consumeInvite` is the one method with a real concurrency requirement.** Two
simultaneous redemptions of a `maxUses: 1` invite must not both succeed, so the
check and the increment cannot be separate round trips. The contract requires
one atomic statement - in SQL:

```sql
UPDATE chatpack_conversation_invites
   SET uses = uses + 1
 WHERE code = $1
   AND (max_uses IS NULL OR uses < max_uses)
   AND (expires_at IS NULL OR expires_at > now())
RETURNING *
```

Zero rows returned means "not usable any more", which the adapter reports as
`null`. Core distinguishes 404 from 410 by calling `getInvite` first: a
successful get followed by a null consume means expired or exhausted (or lost a
race - the same answer to the user either way).

**Not atomic across methods:** consume-then-add-participant is two adapter
calls, and the contract has never carried cross-method transactions. If the add
fails after the consume, a _use_ is burnt but no membership is wrong. Losing a
use is recoverable (mint another invite); the alternative is a transaction
primitive in the adapter interface, which is a much larger change than this
feature earns.

### 3. Core generates the token; it is stored in plaintext

**Core generates it**, via `crypto.getRandomValues` into 32 bytes of base64url
(256 bits, URL-safe by construction, no padding). This is a deliberate
departure from ids, which adapters generate (ADR 0001): an id needs to be
unique, a token needs to be **unguessable**, and entropy is a security property,
not a storage detail. If adapters minted tokens, one could reach for
`Math.random()` and nothing would fail a test - it would just be brute-forcible.
Core generating it means every backend gets the same guarantee.

**It is stored as-is, not hashed.** This is the security tradeoff in the ADR and
it deserves stating plainly rather than defaulting to "hash it like a password."
An invite code is not a credential proving who you are; it is a **capability
URL** - the same class of object as a Google Docs share link or a Dropbox
link - where possession _is_ the permission. That is the entire point of a link
invite. Hashing would mean the plaintext exists exactly once, at creation, and
an admin could never re-display the link they already handed out, which is a
feature every chat product ships.

What bounds the blast radius instead of hashing:

- **Revocation** - `DELETE` removes the row; a revoked code is indistinguishable
  from one that never existed (`INVITE_NOT_FOUND`).
- **Expiry** (`expiresAt`) and **use caps** (`maxUses`), both enforced inside
  the atomic consume.
- The code grants membership of one group and nothing else - no identity, no
  other conversation, no elevation to admin.

Honest consequence: the code appears in the request path
(`POST /invites/:code/accept`), so it lands in ordinary HTTP access logs. We
took that over a body-carried code anyway, because `GET /invites/:code` is what
every client and every AI builder will guess, and guessability is a stated
project goal. Anyone whose threat model includes their own access logs should
set a short `expiresAt`. Documented, not hidden.

### 4. The invite carries the approval policy

`requiresApproval: false` (default) - redeeming adds you as a `member`
immediately. `requiresApproval: true` - redeeming creates a **pending
`JoinRequest`** instead, and an admin resolves it.

The policy belongs on the invite rather than on the conversation because it is
per-link in practice: one no-approval link for the team, one approval-gated
link for a public page, same group. A column on `conversations` would force a
single policy per group and cost a schema change on an existing table; a
boolean on a new table costs nothing and is strictly more expressive.

It also means join requests are reachable two ways - from a link, or directly
via `requestToJoin` for a group the user already knows the id of - with one
resolution path for the admin either way.

### 5. Redemption is idempotent; a join request from a member is an error

Following ADR 0017 §3, replays must be harmless:

- **Redeeming an invite you have already used** (i.e. you are already a
  participant) returns the conversation and **does not consume a use**. There is
  a correct value to return, so returning it beats an error.
- **Requesting to join a group you are already in** throws `ALREADY_PARTICIPANT`
  (409). There is no `JoinRequest` that honestly represents "you're already in",
  and inventing a synthetic approved one would be a lie the client then has to
  special-case.

That split is the general rule this ADR follows: **idempotent where a truthful
success value exists, explicit error where none does.**

**The order of the checks inside `acceptInvite` is load-bearing**, and both
orderings that look natural are wrong. Implementation found two:

1. **The 410 check must come after the idempotent shortcuts**, not with the 404
   lookup. Checking usability up front means a double-clicked `maxUses: 1` link
   answers `INVITE_EXPIRED` to the very person it just admitted - the one caller
   who has an unambiguously correct answer waiting. The lookup throws 404 for an
   unknown code; the 410 only fires once the call is actually going to spend a
   use. Same for someone whose approval-gated request is already pending.
2. **The participant cap must be checked before consuming**, not after. The cap
   lives in the shared admit path, which runs after `consumeInvite`, so
   redeeming into a full group would return 422 _and_ silently burn one of the
   link's redemptions. §2 accepts losing a use to a crash between two adapter
   calls; losing one to a predictable, fully-anticipated refusal is just a bug.

Both are regression-tested. The general shape: an idempotent operation has to
decide _whether it is a replay_ before it decides _whether it is allowed_.

A **denied** request is kept (status `denied`) so the requester can be told, and
a later request from the same user replaces it with a fresh `pending` one -
`(conversationId, userId)` is unique, one row per user per group. Denial is
therefore not a block: blocking a user from ever re-requesting is a moderation
feature (with its own list, its own permissions) and is out of scope here.

### 6. No new transport event types

Joining publishes the **existing** `participant.added` `ConversationEvent` from
ADR 0017 §4 - a redeemed invite and an admin-initiated add are the same change
to the same list, so members and the joiner both get the live update for free,
and an approved join request does too.

Deliberately **not** added: a `join_request.created` event telling admins a
request is waiting. ADR 0017 §4 argued hard _for_ membership events, so the
asymmetry needs a reason. There, absence of an event meant members watched a
five-person group while a sixth was already talking - a conversation that was
**visibly inconsistent**. A pending join request is a **moderation queue**: the
requester is not in the conversation, nothing on screen is wrong, and the only
cost of learning late is latency on an admin action. Against that:
`ConversationEvent` is typed by a hardcoded three-way check in
`isConversationEvent`, and `@chatpack/transport-redis` branches on that guard to
decide which dates to revive - the exact seam where ADR 0017 shipped a bug that
silently dropped every membership event between nodes. Growing that union buys a
badge and re-opens a proven trap.

Admins poll `GET /conversations/:id/join-requests`. If real demand appears, a
later ADR adds the event and updates the guard, the redis decoder, and its
round-trip test together.

### 7. Routes

| Method | Path                                            | Body / query                                                    | Who               |
| ------ | ----------------------------------------------- | --------------------------------------------------------------- | ----------------- |
| POST   | `/conversations/:id/invites`                    | `{ expiresInSeconds?, maxUses?, requiresApproval?, metadata? }` | invite authority  |
| GET    | `/conversations/:id/invites`                    | -                                                               | admin             |
| DELETE | `/conversations/:id/invites/:code`              | -                                                               | admin             |
| GET    | `/invites/:code`                                | -                                                               | any authenticated |
| POST   | `/invites/:code/accept`                         | `{ message? }`                                                  | any authenticated |
| POST   | `/conversations/:id/join-requests`              | `{ message? }`                                                  | any authenticated |
| GET    | `/conversations/:id/join-requests?status&limit` | -                                                               | admin             |
| PATCH  | `/conversations/:id/join-requests`              | `{ userId, decision: "approve" \| "deny" }`                     | admin             |

**No new HTTP verbs** - the ADR 0013 rule holds, all five are already exported
by `ChatpackHandler`, so nothing 405s in an already-mounted app.

`:code` sits in the path here even though ADR 0013 put reaction emoji in the
body. The reason those differ: an emoji is arbitrary Unicode that
percent-encodes into a manglable segment, while an invite code is base64url -
URL-safe by construction with nothing to escape.

`GET /invites/:code` requires authentication like every other route (the auth
hook runs before routing - `llms.txt` hard rules). Previewing tells you what you
are joining; it is not an anonymous endpoint.

`PATCH .../join-requests` addresses the request by `userId` rather than its `id`,
because `(conversationId, userId)` is already unique and an admin acting on a
moderation list has the user in hand.

### 8. Invite creation has its own permission hook

`PermissionHooks` gains `canInvite`, defaulting to the same admin check as
`canManage`:

```ts
canInvite?: (ctx: PermissionContext) => Promise<boolean> | boolean;
```

Everything else here - listing invites, revoking, listing and resolving join
requests - is gated by the existing `canManage`.

A fourth hook needs justifying. "Any member may invite, but only admins may
remove people" is the single most common variation of this feature (Discord
splits exactly there), and without `canInvite` the only way to express it is to
loosen `canManage`, which also hands every member the power to **remove**
others and **rewrite roles**. A permission model whose only escape hatch
over-grants is a broken permission model. Defaulting `canInvite` to the admin
check means no existing deployment changes behavior.

Note the asymmetry it creates on purpose: creating an invite can be delegated to
members, but _resolving_ a join request cannot. Minting a link is a weaker act
than admitting a specific person - the link still requires the invitee to act,
and an approval-gated link routes back through an admin anyway.

### 9. New error codes

| Code                     | Status | When                                                        |
| ------------------------ | ------ | ----------------------------------------------------------- |
| `INVITES_UNSUPPORTED`    | 501    | the adapter has no `invites` capability                     |
| `INVITE_NOT_FOUND`       | 404    | unknown or revoked code                                     |
| `INVITE_EXPIRED`         | 410    | past `expiresAt`, or `maxUses` exhausted                    |
| `INVITE_LIMIT_EXCEEDED`  | 422    | the group already holds `MAX_INVITES_PER_CONVERSATION` (50) |
| `JOIN_REQUEST_NOT_FOUND` | 404    | resolving a request that does not exist                     |
| `ALREADY_PARTICIPANT`    | 409    | requesting to join a group the caller is already in (§5)    |

`410 Gone` is the second non-4xx-or-409 status in `STATUS_BY_CODE` after
`SEARCH_UNSUPPORTED`'s 501, and it is exactly right: the invite was here and is
permanently not any more. One code covers both time-expiry and use-exhaustion
because the client handling is identical ("ask for a new link"); the _message_
says which.

Reused unchanged: `NOT_GROUP_CONVERSATION` (a DM has no invites - its membership
is fixed by `pairKey`), `NOT_CONVERSATION_ADMIN`, `GROUP_LIMIT_EXCEEDED` (a
redemption that would exceed 256 participants, checked **before** consuming a
use), `CONVERSATION_NOT_FOUND`, `INVALID_INPUT`.

### 10. The preview is minimal on purpose

`GET /invites/:code` returns an `InvitePreview`, **not** a `Conversation`:

```ts
interface InvitePreview {
  conversationId: string;
  name: string | null;
  participantCount: number;
  requiresApproval: boolean;
  invitedBy: string;
  /** `true` when the caller is already in, so accepting is a no-op. */
  alreadyParticipant: boolean;
}
```

`alreadyParticipant` is the one field that is about the caller rather than the
group, and it earns its place: without it a client cannot tell "Join this group"
from "Open this group" before rendering the button, and the only way to find out
would be to accept the link and see what happens. It leaks nothing - the caller
already knows whether they are a member.

Returning the conversation would hand **every member's user id** to anyone
holding a link, before they join and whether or not they ever do - a membership
enumeration leak triggered by the one route that must be reachable by
non-members. A count answers "is this the right group and is it active?" without
naming anyone. No messages, no participant list, no metadata.

This is why the preview is a separate shape rather than reusing
`api.getConversation`: that method requires read permission, correctly refuses a
non-member, and must keep doing so.

## Consequences

- **Not breaking for custom adapters.** The required contract stays at nineteen
  methods; `invites` is optional, and an adapter without it makes the eight new
  routes return 501. `llms.txt` Part 2 gains the capability as an opt-in
  section, alongside `searchMessages`.
- **Postgres deployments must run the migration again** for two new tables,
  `chatpack_conversation_invites` and `chatpack_join_requests`. All statements
  stay idempotent, and unlike the ADR 0017 migration this one only adds tables -
  no column changes, no index swap, so it is safe to run before deploying.
- **`chat.api` grows by eight methods** (`createInvite`, `listInvites`,
  `revokeInvite`, `getInvitePreview`, `acceptInvite`, `requestToJoin`,
  `listJoinRequests`, `resolveJoinRequest`), the largest single addition since
  the original nine. The "nothing else exists" list in `CLAUDE.md`, `llms.txt`
  and the skill all have to be exhaustive again.
- **`@chatpack/client` does not wrap any of this yet**, the same deliberate lag
  groups had between core 0.7.0 and client 0.5.0. Hosts call `fetch` against
  the eight routes until it does. Worth doing next, because an invite flow is
  mostly UI.
- **Expired invites are never garbage-collected.** A row past `expiresAt` stays
  until revoked; consume refuses it, so it is inert, and `listInvites` shows it
  as expired rather than pretending it is gone. Bounded by
  `MAX_INVITES_PER_CONVERSATION`, so it cannot grow without limit - but an app
  minting short-lived links forever will want a periodic delete. There is no
  Chatpack-side sweeper: a background job is deployment shape, not library
  scope.
- **Denial is not blocking.** A denied user may request again (§5). Apps needing
  a hard block implement it in `canRead`/`canInvite` or above Chatpack.
- **No telemetry counters were added.** The set stays at `messagesSent` and
  `conversationsCreated` (MVP §12) - counting invites would mean a new anonymous
  aggregate for a feature whose adoption we can already infer from group counts.

## Alternatives considered

- **One `PendingMembership` table with a `direction` column** - fewer tables,
  but half the columns are null per row and "who may create this" becomes a
  runtime branch. See §1.
- **Required adapter methods, like groups** - consistent with ADR 0017, but
  takes custom adapters from nineteen to twenty-eight required methods two
  releases in a row for a feature many apps never call. See §2.
- **Nine individually optional methods** instead of one namespace - matches the
  existing `searchMessages?` shape, but permits a half-implemented capability
  that typechecks and fails at runtime. See §2.
- **Hashing the invite code** - correct for a credential, wrong for a capability
  URL, and it makes re-displaying an existing link impossible. See §3.
- **Adapter-generated codes** - consistent with how ids work, but silently
  permits a weak generator. See §3.
- **`requiresApproval` as a column on `conversations`** - one policy per group,
  a schema change on a hot table, and less expressive than per-link. See §4.
- **A `join_request.created` transport event** - a live moderation badge, at the
  cost of growing a union whose guard has already caused one cross-node data-loss
  bug. See §6.
- **Reusing `canManage` for invite creation** - no new hook, but "members may
  invite" then also grants "members may remove members". See §8.
- **Returning the full `Conversation` from the preview route** - one fewer type,
  and it leaks every member's id to any link holder. See §10.
